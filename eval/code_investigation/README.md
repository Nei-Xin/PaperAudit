# 论文—代码调查评测

这套评测回答一个问题：对“论文里的某个取值或做法，代码里是不是这样”这类追问，多步调查 agent 是否比单次检索更可靠。

- **agent**：模型通过原生工具调用自主查目录、查找、读取指定行、检索论文，结论拆成逐条发现并各带引用（`investigate=True`）。
- **单次检索**：原有流程，规划一次查询、检索一次、回答一次。

留出集上（4 篇开发时未见过的论文，51 题，每题重复 3 次）：

| | agent | 单次检索 |
|---|---|---|
| 与参考标签一致 | 139/153 | 88/153 |
| 参考为不一致，却判一致 | 0 | 0 |
| 参考为一致，却判不一致 | 0 | 3 |
| 每题平均模型请求 / tokens | 6.2 / 22,713 | 2.0 / 8,292 |

这个差距有明确的适用范围，见[局限](#局限)。

## 题目怎么构造

每道题只问一个可比较的点，针对一篇真实论文和它官方仓库的一个固定提交。参考标签有三种：

- **一致**：论文和代码说的是同一件事。
- **不一致**：两者给出不同的取值或做法。
- **未定位**：论文描述了，仓库里没有对应代码。

不一致题主要来自**受控修改**：复制仓库，只改动一个超参数（每处替换的出现次数都有断言，帮助文本和文档里的同一取值一并替换），然后在原仓库和修改版上问同一个问题。这样同一道题既有一致版本也有不一致版本，模型不能靠“总是说一致”得分。另有少量天然不一致，例如 LoRA 论文写 A 用随机高斯初始化，而 `loralib` 用的是 Kaiming uniform。

参考标签逐条对照源码和解析后的论文原文核实，不进入任何提示词。

| | 论文与仓库 | 题数 | 一致 / 不一致 / 未定位 |
|---|---|---|---|
| 开发集 `cases.json` | MoCo、GCN、MAE、LoRA | 39 | 22 / 13 / 4 |
| 留出集 `cases_holdout.json` | SimSiam、GAT、DINO、DDPM | 51 | 28 / 19 / 4 |

论文版本、仓库提交和文件哈希都记录在题库里。

## 怎么评分

两种流程映射到同一组标签：一致、不一致、未定位、部分对应、混合、弃权、错误。

- 失败和弃权都计入分母。
- agent 给出多条发现且判定不同时，只保留文本含题目关键词的发现；仍不同就记为“混合”并算错。
- 单次检索只有一个总关系标签，按固定表映射。
- **方向性错判**单独统计：参考为不一致却判一致，或反过来。这是最不该出现的错误。

## 留出集的纪律

- 题库在运行前冻结，哈希记录在 `holdout_freeze.json`。
- `check_isolation.py` 检查留出集与开发集在论文、仓库、文件哈希和题目上没有重叠，并确认题库冻结后未改动。
- 运行前写明提交、重复次数和主指标；只运行一次；评分规则在看到结果后不改。
- 留出集现在已经被看过，之后再用这 51 题只能算开发集。

### 开发集上的四次运行

开发集用来发现问题和验证修复，这里的数字都是看着失败改出来的，不是独立结果。

| 运行 | 说明 | agent | 单次检索 |
|---|---|---|---|
| 1 | 首次运行，每题 1 次 | 32/39 | 25/39 |
| 2 | 放宽论文引文比对后，每题 1 次 | 30/39 | — |
| 3 | 与运行 2 相同的代码，每题 3 次 | 90/117 | 75/117 |
| 4 | 修复弃权问题后，每题 3 次 | 99/117 | — |

- 运行 3 中 agent 的 27 条不匹配里有 12 条是弃权，原因包括：片段编号连同页码一起抄、引文过长、引文带省略号或行号、格式错误占用了唯一一次引用修正、论文检索搜不到只陈述一个数值的短句。运行 4 逐项修复后弃权降到 2 条，用掉引用修正的运行从 35/117 降到 9/117。

## 已知问题

- **agent 分不清“未定位”和“不一致”。** 它倾向于说“代码实现的是别的，所以不一致”。开发集 0/12，留出集 6/12，都不如单次检索。
- **逐字引用不等于引用支持结论。** 开发集上出现过：论文表格文本是 `warmup epochs [20] 40`，其中 `[20]` 是参考文献编号，模型把它读成取值 20 并判为一致。引文确实存在，校验查不出这类误读。留出集上没有出现，但也没有修。
- **摘要正文不受逐条发现约束。** 出现过摘要写“不一致”、提交的发现里却只有一条“一致”的情况。
- **评分规则处理不了一题多点。** 一题含两个参数且一对一错时会被记为“混合”。

## 局限

- 题目和 agent 出自同一人。题型以“在某个文件里查一个取值”为主，正是多步查找的强项；需要理解算法逻辑的问题没有覆盖，差距不能外推。
- 单人标注，没有独立复核。留出集里已发现一处标注疏漏。
- 共 8 篇论文，都是机器学习方向、有小型官方仓库的论文。
- 不一致题大多是受控修改，不代表真实仓库里不一致的分布。
- 所有结果来自同一个模型配置（OpenAI 兼容接口，支持原生工具调用），对应各次运行记录中配置的模型。
- 单次检索流程在评测前补上了“不一致”标签（原提示词里没有这个选项）；没有做其他调优。

## 规划与人工审阅流程验收

`planning.py` 比较单次规划与自主阅读规划，在相同论文、仓库和目标数量下交替运行三次；两者只比较前 N 个有效要点。固定输入哈希和代码哈希先写入协议，每次付费运行前留下派发标记，已有输出目录不允许自动覆盖或续跑。

```sh

uv run --locked python -m eval.code_investigation.planning --data eval/code_investigation/data --output tmp/planning-dry

# 真实模型：三轮规划对照，再从落盘规划中选择前五项和一个补充问题执行
uv run --locked python -m eval.code_investigation.planning --data eval/code_investigation/data --output tmp/planning-mae --run --execute
```

规划通过真实 API 任务路径运行；执行前重建应用生命周期，验证重启后恢复、所选项隔离、自定义问题、重复提交复用及总预算。数据全部写入输出目录中的独立项目库，不修改现有项目。

关键词匹配仅生成供人工复核的候选，不能直接称为语义覆盖率。人工复核须确认实验设置、对象与参数一致，并同时报告成本、有效要点数、拒绝次数和失败情况。该验收使用已知开发论文，不属于独立留出结果，也不验证整个仓库的算法正确性。

### 规划节奏 v2 的对照方法

v2 不增加总预算：仍为 12 次请求、240 秒、24 次阅读工具调用；仅调整预算内的调度。每轮最多执行 3 个阅读调用，读取论文后下一轮只允许提交要点、声明当前片段没有更多要点或结束。最后 3 次请求只允许提交和修正；完全相同的成功读取不会重复执行。没有可核对信息时可以继续阅读，不强迫模型编造要点。

对照沿用同一 MAE 输入、模型与目标 20 项，各策略运行 3 次，不自动重跑失败。单次规划最多 3 次请求，自主规划最多 12 次且空结果回退最多另用 3 次；这是固定的各策略上限，并非两者强制花费相同请求数。除用量外，记录第一次提出与第一次接受要点之前的成功阅读次数，以检验是否真正改变了节奏。

覆盖规则在运行前写入协议：检查前 20 个有效要点的主题、问题与引文，要求同一实验设置下明确核对参考参数或做法，且引文给出所需取值或方法。复合参考题可由多个要点共同覆盖，但缺少任一部分只计部分覆盖；只在无关问题的引文里出现关键词不算覆盖。失败或空规划计零分，部分覆盖不计入完全覆盖分子。逐题记录理由，并注明评定者；本轮仍是开发数据，不构成独立留出结果。

## 发现的证据支持复核

复核者只读取引用校验已通过的逐条发现、原判定、完整论文片段和代码行，不读取调查轨迹、摘要、对话历史或其他子任务。它无工具，先分别复述两侧的值或做法，再判断这些证据是否支持原判定。每次调查批量复核全部“一致／不一致／部分对应”发现，最多一次请求；因此同批发现彼此可见，提示词要求逐条独立判断，但这不等于逐条完全隔离。“未定位”不复核。

`verification.status` 为 `passed`、`failed` 或 `not_reviewed`，保留原 `verdict`。语义复核未通过，或已要求复核但服务失败、格式无效、预算耗尽时，都标为“待核对”，不改成另一个判定，不计入确认的一致／不一致数量。旧数据的默认值为未复核且未要求复核，仍可读取。复核响应必须包含所有输入发现的编号且不重复；没有额外格式重试，也没有 SDK 隐藏重试。超出 120,000 字符的证据批次不截断，而是保留为待核对。

一致性审计默认启用；追问中的工具调查由 `PAPERAUDIT_CODE_VERIFICATION` 控制。启用时单项预算由 11 增至 12，调查仍最多使用前 11 次，最后一次留给复核；总审计上限保持 160。模型服务失败仍消耗请求预算。复核未通过时，摘要由程序根据每条发现的当前状态生成，避免原来的肯定摘要盖过“待核对”标记。


开发对照为 39 题各三次：每题只生成一次调查结果，再对这份完全相同的结果做一次复核。这样衡量的是复核对相同证据的作用，不能声称比较了两套独立生成的端到端系统。调查最多 11 次请求，不回退到单次检索；复核后最多 12 次，与生产流程相同地共用 180 秒截止时间。全轮含固定验收最多 1,413 次请求。

同一个模型调查并复核自己，可能重复同样的误读。隔离调查上下文和先复述证据只能缓解，不能保证正确。数据来自已知开发集，没有独立留出结论，也没有独立人工标注。

### 实现与约束

`agents/repo_mapper.py` 生成短地图，只能使用 `list_dir`、`find_symbol` 和 `read_file`；最多 4 次模型请求、120 秒，每轮最多执行 4 个调用，最后一次强制提交。没有论文、问题、参考标签或旧发现输入。地图最多 10 个位置，路径、行号和职责合计不超过 1500 字符。生成时校验每项位置的所有行确实读过；职责是模型写的导航说明，**程序不能保证职责描述在语义上正确**。

启用方式为 `PAPERAUDIT_REPO_MAP=true`；初始默认关闭，按冻结对照结果决定是否调整。先规划后执行时，在人工批准后、分派调查前生成；规划任务本身不生成地图。一步审计在规划后生成。剩余总预算至少容纳地图的 4 次和一项调查的 12 次才生成，否则直接调查。生成请求计入原有总上限，不扩大 160 次预算；生成失败或空结果保留费用和停止原因，调查仍可继续。空地图不写入缓存，后续新审计可能再次尝试生成；本轮按每个版本一次生成计费，不代表多次失败审计的成本。

地图保存到项目的 `repo-map.json`，记录完整代码索引的哈希和地图版本。读取时检查二者，代码上传替换时删除旧文件；保存时再次检查当前索引，拒绝生成期间已过期的地图。文件使用现有串行、原子写入；后台审计沿用单 worker。每次调查工作区独立，地图只作为带不可信标记的导航提示，地图读取过的行不进入调查的已读集合。发现仍须重新读取实际代码后通过引用校验。不会把调查结论写回地图。

一致性报告记录本次地图、是否复用、新增请求和 tokens；生成成本与复用成本分开。刷新或重启后可复用；已有旧报告默认无地图。已启用的追问只复用当前有效地图，不为一次追问自动生成。设置随后台任务快照保存，重试保留原选择。页面可展开查看地图和路径，不把它展示成支持结论的证据。

## 实时进度与持久事件

第五步是工程能力验收，不做准确率对照。规划、要点接受、子任务排队／开始、工具步骤、复核和子任务结束，通过可选回调追加到项目的 `consistency-jobs/<job_id>.events.jsonl`。它展示完成的工具步骤与判定摘要，不是模型逐 token 流式输出，也不展示模型原始回复或推理文本。工具参数采用白名单与长度限制，模型提交内容不直接进入事件。

每个任务有从 1 开始的连续事件编号；写入在单进程存储锁内完成并 flush/fsync。SSE 路由为 `GET /api/projects/{pid}/consistency-jobs/{job_id}/events`，先回放再追踪；原生 EventSource 断线自动携带 `Last-Event-ID`（优先于 `after` 查询参数），页面刷新从头回放，前端按编号去重。每 0.5 秒读取新增日志，15 秒心跳，设置 `Cache-Control: no-store` 和 `X-Accel-Buffering: no`。最终状态事件先落盘，再发布任务结束状态；连接排空日志后发出 `end`，前端关闭连接，卸载页面也会清理连接。

事件日志是可降级的观察记录，任务 JSON 和最终报告仍为结果来源。日志写入失败不阻止调查和报告保存；日志不可读时停止流并退回既有任务轮询。重启时运行中任务标记为中断，已有步骤可回看；旧任务没有日志也可继续查看报告。当前仅支持一个 worker 进程，没有跨进程写入锁、任务取消、事件压缩或日志轮转；事件不会记录完整论文、代码和发现正文。SSE 连接、重连和回放都不触发模型请求。

本地验收：后端 638 项测试、浏览器 8 项流程、前端类型生成与生产构建通过。新增测试覆盖并发顺序、断尾恢复、归属检查、游标校验、日志损坏／不可写降级、心跳、断连、超过单批日志的末尾排空，以及实际任务事件与不变的模型请求数。浏览器测试在任务仍运行时显示工具步骤，模拟断线与重复事件，检查服务端收到续传游标，刷新后补齐；成功和失败均结束连接，桌面与手机无横向溢出。
