# 审计记录持久化、工作区上传与后台执行：`/goal` 执行文档

> 文档用途：供 Codex `/goal` 在用户离开期间自主执行。  
> 当前项目：Hy3 论文学习助手（Streamlit）  
> 本轮目标：允许用户在已打开的论文项目中上传另一份报告进行审计；审计在后台执行，完成后保存为可恢复、可查看的项目历史记录。  
> 实施原则：沿用现有项目文件夹、JSON 原子写入和审计服务，不引入 SQLite、Redis、Celery 或独立服务，不重构审计算法。

这里的“后台执行”特指：**在当前 Streamlit Python 进程内使用单线程执行器运行，页面提交后不阻塞用户继续阅读**。它不表示关闭应用后任务仍会继续，也不表示第一版需要部署独立 Worker。

## 一、可直接用于 `/goal` 的任务描述

```text
按照 docs/3.audit-history-persistence-goal.md 完成“审计记录持久化、工作区上传与后台执行”第一版开发。

要求：
1. 在已打开的论文学习项目中增加“审计其他报告”，支持粘贴文本以及上传 .txt/.md；复用当前论文原文和 ParsedPaper，不要求重新上传 PDF。
2. “审计当前讲解”和“审计其他报告”都提交为后台任务；提交后立即返回阅读工作区，用户可以继续阅读、提问或切换项目。
3. 使用单进程内 ThreadPoolExecutor(max_workers=1) 执行审计，额外任务排队；后台线程不得直接访问 st.session_state 或调用任何 st.* API。
4. 任务状态和进度必须原子写入当前项目的 audit-jobs 目录；UI 使用轻量定时轮询展示排队、运行、成功、失败或中断状态。
5. 每次审计成功后，将完整 AuditRun 自动保存到当前论文项目的 audits 目录；刷新页面或重新打开项目后仍可查看。
6. 同一论文允许保存多次审计，历史记录不可相互覆盖，并且必须绑定当时被审计报告的内容哈希。
7. 在“报告操作”中增加“审计任务（N）”和“审计记录（N）”入口，支持查看进度、打开历史结果及返回论文讲解。
8. 保存模型名称、推理强度、检索 Top-K 和研判批大小，但严禁保存 API Key、隐藏推理过程或其他凭据。
9. 应用进程退出后第一版不恢复执行；下次启动时将遗留 QUEUED/RUNNING 任务标记为 INTERRUPTED，并允许用户重新提交。
10. 使用项目现有的 JSON、Pydantic 模型和原子写入工具；不增加数据库、账号、云同步或复杂版本管理。
11. 不修改审计评分、标签定义、检索和判断算法；只完成上传、后台任务、保存、恢复、历史查看和必要错误提示。
12. 完成任务存储、后台执行、主要交互回归、全部测试和编译检查；修复真实阻塞问题后停止。
13. 遇到非关键设计选择时采用本文档默认方案继续，不等待用户确认。
```

## 二、当前问题与完成状态

当前工作区的“报告操作”只能审计系统生成的当前讲解，不能直接上传另一份报告。启动页虽然已有“审计已有报告”，但该入口与已打开的论文项目割裂。

当前审计还在 Streamlit 页面请求中同步执行，完成后只执行：

```python
st.session_state["audit_run"] = audit_run
st.session_state["result_mode"] = "audit"
```

因此存在以下问题：

- 用户不能在阅读当前论文时上传课堂笔记、人工报告或另一份模型报告进行对照审计；
- 审计期间页面被长时间占用，不能继续使用论文阅读和追问；
- 浏览器刷新后记录可能消失；
- 重新打开论文项目后无法查看过去的审计；
- 同一报告多次审计没有历史版本；
- 无法确认某次审计对应的是报告修改前还是修改后的内容；
- 当前项目存储已经保存论文、讲解与问答，但审计数据没有进入 `ProjectStore`。

本轮完成后应形成：

```text
当前讲解或上传报告
→ 创建后台审计任务并立即返回阅读器
→ 后台基于当前论文原文执行审计
→ 保存完整 AuditRun 并完成任务
→ 用户从“审计任务”或“审计记录”打开结果
→ 刷新或重新打开项目后仍可恢复
```

## 三、第一版范围

### 必须完成

- 在当前论文项目的“报告操作”中上传 `.txt/.md` 报告或粘贴文本；
- 上传的报告复用当前项目的论文 PDF 和 `paper-index.json`；
- 审计任务在后台线程执行，不阻塞当前阅读工作区；
- 同一时间最多执行一个审计任务，其余任务进入队列；
- 后台任务状态、进度、阶段、错误和结果 ID 持久化；
- 普通 Streamlit rerun、页面刷新和项目切换不终止仍在同一应用进程中的任务；
- 应用进程重启后将未完成任务标记为 `INTERRUPTED`，不静默假装继续；
- 审计成功后自动保存；
- 同一项目保存多条不可变审计记录；
- 审计记录包含来源、时间、报告哈希、运行配置和完整 `AuditRun`；
- 项目重新打开后可以列出和查看历史审计；
- “审计当前讲解”产生的记录必须保存；
- 当“审计已有报告”能够关联到当前已保存论文项目时，也保存为该项目的审计记录；
- 保存失败时任务不得标记为成功，必须展示明确错误并允许用户重新提交；
- 损坏的单条记录不能阻止其他记录加载；
- 项目最近更新时间随新审计写入而更新；
- 现有论文讲解、论文与代码、内容追问及审计展示保持可用。

### 暂不完成

- `.docx`、报告 PDF 和任意办公文档解析；
- 应用进程关闭或电脑重启后的断点续跑；
- 独立 Worker 进程、Redis、Celery 或消息队列；
- 运行中任务的强制取消；
- 并行执行多个 Hy3 审计任务；
- 两次审计的自动差异对比；
- 审计结果在线编辑；
- 云端同步、账号和多人协作；
- SQLite 或其他数据库；
- 审计记录标签、收藏、搜索和批量管理；
- 自动清理旧记录；
- 定时或计划审计、独立后台服务、桌面/邮件通知；
- 修改审计 Prompt、评分、标签或检索逻辑；
- 为没有学习项目的 PDF 重构一套“审计专用项目”模型。

本轮后台任务只要求覆盖“已打开且已保存的论文学习项目”，这正是新增工作区上传入口所在的位置。启动页中没有对应学习项目的临时“审计已有报告”可以保持现有同步流程，但必须继续正常工作。不要为了这一独立入口新增“审计专用项目”类型或重构项目模型。

第一版的核心闭环应严格限定为：

```text
已保存的论文项目
→ 选择审计当前讲解，或上传/粘贴另一份报告
→ 创建持久化任务并进入进程内单线程队列
→ 用户立即返回论文工作区继续操作
→ 审计成功后写入该项目历史
→ 刷新或重新打开项目后仍可查看结果
```

没有已保存论文项目时，不创建后台任务；继续沿用现有临时审计入口即可。

## 四、磁盘结构

沿用现有项目目录：

```text
PaperAuditData/
└─ projects/
   └─ <project_id>/
      ├─ metadata.json
      ├─ paper.pdf
      ├─ paper-index.json
      ├─ learning-report.json
      ├─ codebase.json              # 可选
      ├─ session.json
      ├─ audit-jobs/
      │  ├─ audit-job-20260825T091500Z-a31f.json
      │  └─ audit-job-20260825T091530Z-bc20.json
      └─ audits/
         ├─ index.json
         ├─ audit-20260824T143025Z-a31f.json
         └─ audit-20260824T161208Z-c820.json
```

规则：

- `paper.pdf`、论文索引、讲解和代码索引不得复制到每条审计中；
- 完整审计记录单独保存；
- `index.json` 只保存历史列表所需的轻量摘要；
- 审计文件名使用 UTC 时间和短随机后缀，避免同秒覆盖；
- 任务输入的报告文本必须在提交时写入任务文件，后台线程不得依赖会随 rerun 消失的 `UploadedFile`；
- 所有 JSON 使用 UTF-8、`ensure_ascii=False` 和现有原子写入机制；
- 不自动删除历史记录。

## 五、数据模型

### 5.1 审计来源

使用稳定字符串，不需要引入复杂枚举迁移：

```text
generated_learning_report  # 系统生成的当前论文讲解
uploaded_report            # 用户上传或粘贴的已有报告
```

### 5.2 审计索引元数据

在 `src/paperaudit/storage.py` 中增加最小存储模型，命名可按现有风格微调：

```python
@dataclass(frozen=True)
class AuditRecordMetadata:
    audit_id: str
    project_id: str
    created_at: str
    source_type: str
    source_label: str
    report_hash: str
    grade: str
    total_score: float | None
    audit_coverage: float
    critical_count: int
    high_count: int
    model: str
    reasoning_effort: str
```

索引文件示例：

```json
{
  "schema_version": 1,
  "records": [
    {
      "audit_id": "audit-20260824T143025Z-a31f",
      "project_id": "f7a42f85cf1e2431",
      "created_at": "2026-08-24T14:30:25+00:00",
      "source_type": "generated_learning_report",
      "source_label": "当前论文讲解",
      "report_hash": "37d1...c40a",
      "grade": "review",
      "total_score": 74.0,
      "audit_coverage": 0.86,
      "critical_count": 0,
      "high_count": 2,
      "model": "gpt-5.6-luna",
      "reasoning_effort": "high"
    }
  ]
}
```

具体 `grade` 值应使用现有 `TrustGrade` 的真实序列化值，不硬编码示例中的字符串。

### 5.3 完整审计记录

单条记录使用一个带版本的 envelope：

```json
{
  "schema_version": 1,
  "metadata": {
    "audit_id": "audit-20260824T143025Z-a31f",
    "project_id": "f7a42f85cf1e2431",
    "created_at": "2026-08-24T14:30:25+00:00",
    "source_type": "generated_learning_report",
    "source_label": "当前论文讲解",
    "report_hash": "37d1...c40a",
    "grade": "review",
    "total_score": 74.0,
    "audit_coverage": 0.86,
    "critical_count": 0,
    "high_count": 2,
    "model": "gpt-5.6-luna",
    "reasoning_effort": "high"
  },
  "runtime": {
    "retrieval_top_k": 5,
    "judge_batch_size": 6
  },
  "run": {}
}
```

`run` 必须直接保存现有 `AuditRun.model_dump(mode="json")` 的完整结果，包括：

- 被审计报告文本快照；
- 原子论断；
- 候选证据；
- 判断标签、解释和建议；
- 错误类型与严重程度；
- 维度得分；
- 总分、可信等级和覆盖率；
- PDF 解析警告。

不要在 envelope 中再次复制报告文本，因为 `AuditRun.report_text` 已经是被审计版本的快照。

### 5.4 报告哈希

统一使用：

```python
sha256(audit_run.report_text.encode("utf-8")).hexdigest()
```

作用：

- 确认审计记录对应的报告版本；
- 将来可判断当前讲解是否已修改；
- 避免把“重新审计”误认为旧结果恢复。

第一版不需要按哈希自动去重。同一报告允许被多次审计，因为模型配置和运行结果可能不同。

### 5.5 后台审计任务

增加严格、可序列化的任务状态：

```text
QUEUED       已提交，等待单线程执行器
RUNNING      正在执行
SUCCEEDED    已完成，并已产生 audit_id
FAILED       审计或结果保存失败
INTERRUPTED  应用进程在任务完成前退出
```

建议最小任务模型：

```python
class AuditJob(StrictModel):
    schema_version: int = 1
    job_id: str
    project_id: str
    created_at: str
    started_at: str | None = None
    completed_at: str | None = None
    source_type: str
    source_label: str
    source_filename: str | None = None
    report_hash: str
    report_text: str
    scope: list[ClaimCategory]
    audit_mode: str
    status: str
    progress: float = 0.0
    stage: str
    audit_id: str | None = None
    error: str | None = None
    runtime: dict[str, Any]
```

要求：

- `report_text` 是提交时的输入快照，任务不能依赖 Session State；
- `runtime` 只保存模型名称、推理强度、Top-K 和批大小；
- API Key 只通过提交任务时捕获的内存 `Settings` 提供给 Worker，绝不落盘；
- `progress` 限制在 `0.0—1.0`；
- `SUCCEEDED` 必须有有效 `audit_id`；
- `FAILED/INTERRUPTED` 显示可理解的简短错误，不保存 traceback；
- 第一版不增加 `CANCELLED`，因为外部 API 请求无法可靠强制中止。

### 6.1 安全与校验

- 复用现有 `_project_dir()` 对项目 ID 的校验；
- 对 `audit_id` 和 `job_id` 做严格字符校验，只允许字母、数字和连字符；
- 保存前确认项目目录和 `metadata.json` 已存在；
- `source_type` 只允许两种定义值；
- 加载时使用 `AuditRun.model_validate(...)`，不能直接信任磁盘 JSON；
- 不保存 API Key；
- 不保存模型隐藏推理内容；
- 不把 API Base URL 写入审计记录；
- 不把 API Key、请求 Header 或完整 `Settings` 写入任务记录；
- 用户报告和论文原文按现有本地存储边界处理。

### 6.2 写入顺序

采用：

```text
1. 构造 metadata 和完整 envelope
2. 原子写入单条 audit JSON
3. 原子更新 audits/index.json
4. 更新项目 metadata.json 的 updated_at
5. 返回 AuditRecordMetadata
```

若第 2 步失败，不更新索引。若索引损坏或缺失，`list_audit_runs()` 应能扫描 `audits/audit-*.json` 恢复有效记录并重建索引。只需覆盖真实可能发生的单文件损坏，不做复杂事务系统。

### 6.3 排序

历史记录按 `created_at` 倒序返回，最新记录在最上方。

审计任务按 `created_at` 倒序返回；UI 默认只突出未完成任务和最近少量已完成任务，完整成功结果由“审计记录”承担。

## 七、应用接入

### 7.1 工作区上传其他报告

当前启动页已经支持粘贴文本和上传 `.txt/.md`，应复用 `_read_report_file()`，不要另写不一致的解析逻辑。

在 `render_learning_workspace()` 的“报告操作”中增加“审计其他报告…”，点击后使用 `st.dialog` 打开：

```text
审计其他报告

[ 上传文件 ] [ 粘贴文本 ]
支持 .txt / .md

审计范围
● 完整解读
○ 自定义重点

[取消] [在后台开始审计]
```

要求：

- 复用当前项目的 `ParsedPaper`，不重新上传或解析论文 PDF；
- 上传内容必须在提交任务前读取成字符串；
- 文件为空、解码失败或报告只有空白时不创建任务；
- `.txt/.md` 的文本长度沿用现有报告输入限制；
- 弹窗关闭后不应污染当前论文、页码、高亮或问答状态；
- 第一版不支持 `.docx` 和报告 PDF。

### 7.2 后台任务管理器

新增一个聚焦模块，例如：

```text
src/paperaudit/audit_jobs.py
```

职责：

- 持有 `ThreadPoolExecutor(max_workers=1)`；
- 防止同一 `job_id` 重复提交；
- 根据项目 ID 和任务 ID加载任务输入；
- 在 Worker 内创建独立 `AuditService`；
- 将 `AuditService.audit()` 的 progress callback 转换为任务 JSON 更新；
- 完成后调用 `ProjectStore.save_audit_run()`；
- 最后把任务更新为 `SUCCEEDED` 或 `FAILED`。

Streamlit 层通过 `st.cache_resource` 获得进程内唯一的任务管理器。不要在每次脚本 rerun 时重新创建线程池。

后台 Worker 严禁调用：

```python
st.session_state
st.progress
st.status
st.toast
st.rerun
```

Worker 只能调用核心服务与存储接口。UI 所有变化由页面线程轮询磁盘状态后完成。

### 7.3 任务提交

“审计当前讲解”和“审计其他报告”使用同一个提交函数：

```text
1. 验证 active_project_id 与当前论文项目一致
2. 固化 report_text、source_type、source_label、scope 和运行配置
3. ProjectStore.create_audit_job() 原子保存任务输入
4. AuditJobManager.submit(job_id, settings_snapshot)
5. 立即返回阅读工作区
```

`Settings` 快照可以作为线程闭包或任务参数保存在内存，但序列化任务时必须去除 API Key 和 API Base URL。

提交后页面显示简短反馈：

```text
审计任务已提交，可继续阅读论文。
```

不得继续使用覆盖整个页面的同步 `st.spinner()` 或 `st.status()` 等待审计完成。

### 7.4 Worker 执行流程

```text
QUEUED
→ RUNNING：正在准备论文索引
→ RUNNING：正在拆分报告论断
→ RUNNING：正在检索论文证据
→ RUNNING：正在判断论断
→ RUNNING：正在汇总审计结果
→ save_audit_run()
→ SUCCEEDED，并写入 audit_id
```

要求：

- Worker 从保存项目的 `paper-index.json` 恢复 `ParsedPaper`，不依赖当前浏览器 Session；
- progress callback 只写入任务文件，写入应节流，避免每个细小进度都进行磁盘写入；
- 建议只在阶段变化或进度至少增加约 2% 时写入；
- 任意异常都捕获为 `FAILED`，保存简短错误信息；
- API Key 不得出现在错误文本或日志中；
- `save_audit_run()` 成功后才能将任务标记为 `SUCCEEDED`；
- 任务成功后不自动切换用户当前页面。

### 7.5 页面轮询与完成提示

使用 Streamlit fragment 或同等轻量方式，每约 2 秒只刷新任务状态区域，不重绘整个 PDF 和讲解工作区。

轮询区域读取 `ProjectStore.list_audit_jobs(active_project_id)`，展示：

- 排队数量；
- 当前阶段；
- 进度百分比；
- 完成后的“查看结果”；
- 失败或中断后的简短错误。

任务完成后，只有用户点击“查看结果”才执行：

```text
ProjectStore.load_audit_run(project_id, audit_id)
→ st.session_state["audit_run"] = run
→ st.session_state["active_audit_id"] = audit_id
→ st.session_state["audit_origin"] = "history"
→ st.session_state["result_mode"] = "audit"
→ st.rerun()
```

### 7.6 应用重启处理

普通 Streamlit rerun、浏览器刷新和项目切换不应销毁由 `st.cache_resource` 持有的执行器。

如果整个 Streamlit 进程已经退出，第一版不尝试恢复线程。任务管理器在当前 Python 进程中第一次通过 `st.cache_resource` 初始化时执行一次（不能在每次 Streamlit 脚本 rerun 时执行）：

```text
mark_interrupted_audit_jobs()
```

将磁盘中残留的 `QUEUED/RUNNING` 更新为 `INTERRUPTED`，并显示：

```text
应用在任务完成前退出，请重新执行审计。
```

不要将中断任务显示为“仍在处理中”，也不要在没有 API Key 内存上下文的情况下偷偷重启任务。

### 7.7 防止重复提交和重复保存

- 保存动作只能发生在 Worker 一次成功执行后的分支中；
- Streamlit 普通 rerun 不得重新提交任务；
- 相同项目、相同 `report_hash` 已存在 `QUEUED/RUNNING` 任务时，阻止重复提交并提示当前任务；
- 同一报告在前一任务结束后允许再次审计；
- 打开历史记录只加载，不得再次保存；
- 切换项目后后台任务仍写入任务创建时绑定的项目，不能使用当前 Session 中后来变化的项目 ID。

Session State 建议增加：

```text
active_audit_id
audit_save_error
audit_history_open
audit_upload_dialog
```

```text
审计当前讲解
审计其他报告…
审计任务（1）
```

没有记录时显示：


不要单独增加新的顶层导航或长期占用页面的大面板。

### 8.2 任务列表

任务列表保持紧凑：

```text
正在执行
reading-note.md · 45%

等待执行
当前论文讲解

最近完成
reading-note.md · 已完成

```

要求：

- 只显示当前论文项目的任务；
- 页面轮询只更新这一小块区域；
- 进度未知时显示阶段，不伪造精确百分比；
- 第一版不提供强制取消按钮；
- 成功结果通过 `audit_id` 打开；
- 失败和中断任务提供“重新提交”，其行为是创建一个新任务，不能复用旧 job ID。

### 8.3 历史列表

在 popover 内采用紧凑列表，每条显示：

```text
2026-08-24 14:30

覆盖率 86% · 高风险 2
[查看]
```

要求：

- 时间按本地时区显示，磁盘仍保存 UTC ISO 时间；
- `total_score is None` 时显示“未评分”，不能显示 `None 分`；
- 可信等级使用现有中文映射；
- 只有“查看”是第一版必需操作；
- 不为每条记录建立大型卡片，避免再次增加视觉噪音。

### 8.4 查看历史记录

点击“查看”后：

```text
ProjectStore.load_audit_run(...)
→ st.session_state["audit_run"] = run
→ st.session_state["active_audit_id"] = audit_id
→ st.session_state["audit_origin"] = "history"
→ st.session_state["result_mode"] = "audit"
→ st.rerun()
```

审计结果页顶部显示轻量来源信息：

```text
历史审计 · 2026-08-24 14:30 · 当前论文讲解
```

保留“返回论文讲解”。历史记录和刚完成的审计使用同一个 `render_audit_results()`，不要复制一套结果页面。

## 九、错误处理

### 必须覆盖

1. 上传的 `.txt/.md` 为空、编码异常或无法读取；
2. 后台任务创建成功但无法提交到执行器；
3. 执行器中的 Hy3 请求失败或返回结构无效；
4. 审计生成成功但审计历史写入失败；
5. 任务进度文件写入失败；
6. 应用重启后遗留 `QUEUED/RUNNING`；
7. `audits/index.json` 丢失或 JSON 损坏；
8. 某一条 audit JSON 或 job JSON 损坏；
9. 索引引用的 audit 文件不存在；
10. AuditRun schema 不兼容；
11. 当前没有有效项目 ID；
12. 用户在两个项目之间切换后打开任务或历史记录；
13. Streamlit rerun 导致重复执行 UI，但不能重复提交或保存；
14. 保存目录暂时不可写；
15. 总分为空但记录仍可显示。

处理原则：

- 单条损坏记录跳过，并显示简短 warning；
- 其他有效历史仍然可用；
- 后台任务的失败状态必须可见，不能永久停在“处理中”；
- 若 `AuditRun` 已生成但最终保存失败，任务标记为失败并说明“审计已运行，但结果保存失败，请重新提交”；
- 不向用户展示长 traceback；
- 不静默宣称保存成功。

## 十、测试要求

### 10.1 存储单元测试

在现有存储测试或新建聚焦测试中覆盖：

1. `save_audit_run()` 创建 audits 目录、记录文件和索引；
2. 完整 `AuditRun` 保存后可以无损加载；
3. 同一项目连续保存两次不会覆盖；
4. 历史记录按创建时间倒序；
5. `report_hash` 与报告文本 SHA-256 一致；
6. 索引摘要与 `AuditSummary` 一致；
7. 新审计会更新项目 `updated_at`；
8. 无效 project ID 和 audit ID 被拒绝；
9. 不存在的项目不能写入审计；
10. 索引损坏时能够从有效记录重建；
11. 单条记录损坏时其他记录仍可列出；
12. 保存内容中不存在测试 API Key；
13. `total_score=None` 能正常保存与恢复；
14. 创建任务后可以无损加载 `report_text`、scope 和运行配置；
15. 任务状态可以从 `QUEUED` 更新到 `RUNNING/SUCCEEDED/FAILED`；
16. `SUCCEEDED` 任务保存并恢复有效 `audit_id`；
17. `mark_interrupted_audit_jobs()` 只转换未完成任务；
18. job JSON 中不存在 API Key 和 API Base URL；
19. 无效 job ID 被拒绝；
20. 单条损坏任务不会阻止其他任务列出。

### 10.2 后台执行测试

使用 Fake Client 和临时项目目录，至少覆盖：

1. 提交任务后调用方立即返回，不同步等待审计完成；
2. `max_workers=1` 时第二个任务处于排队状态；
3. Worker 使用任务创建时绑定的项目 ID，而不是后来变化的 Session 项目；
4. progress callback 能更新阶段和进度；
5. 成功任务生成一条审计历史并写入 `audit_id`；
6. Hy3 失败会将任务标记为 `FAILED`；
7. 审计成功但结果保存失败时不能标记为 `SUCCEEDED`；
8. 相同报告已有未完成任务时阻止重复提交；
9. 已完成任务允许重新提交形成新任务；
10. 后台代码不导入或调用 Streamlit UI API；
11. 执行器关闭后测试进程能够正常结束，不残留非预期线程。

### 10.3 应用与 UI 回归

至少验证：

1. 当前论文项目可以上传 `.txt/.md` 或粘贴文本创建审计任务；
2. 提交后立即回到论文阅读工作区，PDF 可以继续翻页和滚动；
3. 审计当前讲解也进入同一个后台队列；
4. 任务区域显示排队、进度、阶段、成功和失败状态；
5. 普通页面刷新和项目切换后仍能看到同一进程中的任务状态；
6. 成功任务自动出现一条历史记录；
7. 刷新页面后历史记录仍存在；
8. 重新打开同一论文项目后可查看历史审计；
9. 查看历史审计不会生成重复记录；
10. 返回论文讲解后原讲解、PDF 页码定位和问答仍可使用；
11. 连续提交两次不同审计时第二个排队，最终显示两条记录；
12. 切换项目后不会显示上一项目的任务或审计记录；
13. 应用重启后的遗留任务显示“已中断”，不显示“处理中”；
14. 没有任务和历史记录时界面不报错；
15. 启动页现有“审计已有报告”流程不回归；
16. 现有上传、讲解、论文与代码、内容追问流程不回归。

### 10.4 完成后执行


## 十一、README 更新

在 README 的当前能力或本地保存部分补充：

- 已打开的论文项目支持上传 `.txt/.md` 或粘贴文本进行审计；
- 审计在单进程后台队列中执行，用户可以继续阅读或切换项目；
- 同一时间执行一个审计任务，其余任务排队；
- 停止应用后未完成任务不会断点续跑，重启时标记为中断；
- 审计结果会自动保存到对应论文项目；
- 一个项目可以保留多次审计；
- 历史审计记录包含被审计报告快照和运行配置；
- 数据只保存在用户选择的本地目录；
- 不保存 API Key；
- 没有关联到已保存论文项目的临时审计第一版不会进入历史。

README 还需明确：“后台”仅保证当前应用进程运行期间不阻塞页面；关闭 Streamlit 或电脑后，未完成任务不会继续运行。

不要宣称已经支持：

- 审计差异对比；
- 云同步；
- 多人协作；
- 审计记录全文搜索；
- 独立审计项目管理；
- 应用关闭后的后台持续运行或断点续跑；
- Word 和报告 PDF 上传。

## 十二、最终验收标准

以下条件全部满足才算完成：

- 当前论文工作区可以上传 `.txt/.md` 或粘贴文本审计；
- 审计当前讲解和审计其他报告都通过后台任务执行；
- 提交审计后论文阅读、代码阅读和内容追问不被阻塞；
- 后台执行器只允许一个运行任务并正确排队；
- 任务进度、阶段、失败和中断状态可见且持久化；
- 后台线程不直接操作 Streamlit UI 或 Session State；
- 普通页面 rerun 不会重复提交任务；
- 应用进程重启后遗留任务被标记为 `INTERRUPTED`；
- 审计当前讲解会自动保存；
- 同一论文多次审计不会覆盖；
- 刷新和重新打开项目后可恢复；
- 历史记录能准确显示时间、来源、等级、分数和风险摘要；
- 打开历史记录复用现有审计结果页；
- 每条记录绑定报告文本哈希和完整报告快照；
- 运行配置不包含 API Key；
- 结果保存失败时任务明确标记为失败，不能误报为已完成；
- 页面刷新不会重复提交同一任务；相同项目与相同报告已有未完成任务时给出明确提示；
- 损坏单条记录不阻塞整个项目；
- 损坏单条任务不阻塞其他任务和历史记录；
- 切换项目不会串记录；
- 现有论文学习、代码阅读、追问和审计功能没有回归；
- 全部测试和编译检查通过；
- README 与真实能力一致；
- 没有残留临时文件或临时验证服务。

## 十三、允许自主决策的默认项

执行 `/goal` 时无需因以下事项暂停：

- 审计记录文件名使用 UTC 时间戳加 4–8 位随机十六进制后缀；
- 索引按最新时间倒序；
- 历史列表使用现有绿色强调色和紧凑按钮；
- 时间展示使用本机时区；
- 数据模型放在 `storage.py`，不为少量存储结构新建大型模块；
- 历史结果继续使用现有 `AuditRun` 和 `render_audit_results()`；
- 后台执行使用 `ThreadPoolExecutor(max_workers=1)`；
- 执行器通过 `st.cache_resource` 在普通 rerun 间复用；
- UI 约每 2 秒轮询一次任务状态，优先仅刷新任务 fragment；
- 第一版上传格式仅为 `.txt/.md` 和粘贴文本；
- 不自动删除任何记录；
- 不做同报告哈希去重；
- Fake Client 可以用于确定性测试；
- 真实 Hy3 API 暂时不可用时，只要本地存储与 Fake Client 流程验证通过，就在最终结果中明确说明。

## 十四、停止条件

达到验收标准后停止开发，不继续主动增加：

- 审计记录删除、批量操作或回收站；
- 审计差异视图；
- 图表和统计仪表盘；
- 云端备份；
- 全文搜索；
- 独立审计项目类型；
- 数据库迁移；
- Word、报告 PDF 和其他办公格式解析；
- 独立 Worker、Redis、Celery 和消息队列；
- 应用关闭后的后台持续执行或断点续跑；
- 多任务并行和强制取消；
- 审计 Prompt 或评分体系优化。

这些功能只在用户后续明确要求时再评估。
