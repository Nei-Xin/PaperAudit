# PaperAudit 投稿评审下一阶段长任务

> 用途：复制本文末尾的 `/goal` 内容，作为下一轮持续开发任务。
> 当前范围：单评审流程、问题严重度、证据校验、修改稿对比和质量评估。
> 已明确不做：多人评审、Meta Review、自动投稿、录用概率预测、作者答辩模块和“给作者的问题”模块。

## 一、目标

把 PaperAudit 从“能生成一份评审”提升为“能稳定发现问题、解释问题、验证问题、追踪修改效果”的投稿预审工具。

最终输出应回答四件事：

1. 论文最严重的风险是什么？
2. 这个风险是否有原文证据？
3. 作者应该采取什么具体行动？
4. 修改后问题是否真的被解决？

## 二、当前基线

当前版本已经具备：

- Strong Accept / Weak Accept / Borderline / Weak Reject / Strong Reject 五档建议；
- 评审摘要、核心贡献、优点、接收阻碍、致命问题、必须修改和建议修改；
- PDF 证据定位和原文引文校验；
- 通用 AI/ML、IJCAI、NeurIPS、ICLR、AAAI、自定义评审标准；
- P0/P1/P2/P3 问题严重度基础字段；
- 问题类别、置信度、处理状态和稳定 `issue_id`；
- 修改稿 PDF、差异摘要、评分变化和历史版本；
- 问题列表的严重度、类别、状态筛选与排序；
- 本地项目保存和后台单篇评审任务。

本轮已移除：

- 作者答辩 UI 和答辩后倾向；
- 给作者的问题 UI 和 Markdown 导出；
- 多人评审 / Meta Review 入口和调用链。

## 三、核心设计原则

### 3.1 严重度不等于置信度

- P0 表示问题可能击穿核心结论；
- P1 表示重要且可修复的投稿风险；
- P2 表示完整性或说服力不足；
- P3 表示编辑和表达问题；
- 置信度表示 AI 对问题判断的把握，不代表问题严重程度。

### 3.2 证据优先

- P0/P1 必须绑定 PDF 原文证据，或明确标记为“需人工复核”；
- 禁止模型自行生成页码、表号、引文或实验数字；
- 引文必须在本地 PDF 文本中逐字命中；
- 证据不足时只能降低置信度或降低严重度，不能用流畅措辞掩盖缺证据。

### 3.3 建议必须可执行

每条 P0/P1 至少给出一种具体行动：补实验、补对照、重新定义指标、收窄主张、补充配置、修正公式、增加伦理说明或更正图表。

### 3.4 结论不能伪装成录用预测

系统只给出基于当前论文证据的预审建议，不输出真实会议录用概率，不使用作者身份、机构、引用量等信息推断结果。

## 四、阶段安排

### 阶段 1：建立人工标注回归集（最高优先级）

目标：先知道 AI 分级是否可靠，再继续扩大功能。

任务：

- 从公开 OpenReview 评审中选取 10–20 篇样本；
- 覆盖接收、边缘、弱拒稿、强拒稿和低置信度评审；
- 每条问题人工标注 category、severity、confidence、evidence_valid、actionability；
- 保存固定论文版本 URL（优先 arXiv；若无 arXiv 则使用 PMLR 等公开版本）、OpenReview URL、会议、年份和 reviewer note ID；
- 不保存整篇评审正文，不保存真实身份信息。

验收标准：

- 每个样本都能回到公开来源；
- 至少 80% 的标注问题包含可复核证据或明确的无证据标记；
- 标注格式可以被测试脚本直接读取。

### 阶段 2：离线评估脚本

目标：让每次 Prompt 或模型升级都有可量化对比。

任务：

- 新增 `eval/peer_review_quality.py`；
- 计算问题类别准确率、严重度 Macro-F1、证据命中率、置信度校准误差；
- 单独统计 P0 误报率和 P1 漏报率；
- 统计评审结论与严重度组合的一致性；
- 生成 Markdown/JSON 评估报告。

验收标准：

- 一条命令可以运行完整回归集；
- 报告能比较两个 Prompt 或模型版本；
- P0 误报、无证据高等级问题和评分越界有独立指标。

### 阶段 3：问题抽取质量优化

目标：减少泛化批评、重复问题和无证据问题。

任务：

- 在 Prompt 中加入少量真实评审的“结构化示例”，不复制整篇评论；
- 增加问题去重规则：同一证据、同一主张和相同修复动作合并；
- 增加“事实 / 推断 / 证据不足”字段；
- 对数字、指标、数据集、模型名称和条件做一致性检查；
- 当模型输出无效等级或类别时走安全降级，而不是整篇失败。

验收标准：

- 重复问题数量下降；
- 无证据问题不会被标记为高置信 P0；
- 关键数字与 PDF 原文不一致时显示警告。

阶段 3 实施记录（2026-08-31）：

- 评审 Prompt 增加 3 类结构化校准示例，并明确事实 / 推断 / 证据不足边界；
- 问题去重改为证据锚点或“主张 + 修复动作”一致才合并，避免误删不同证据的问题；
- 增加类别、严重度和置信度的安全规范化；无效值降级为 `other`、P1/P2 或低置信度并标记需复核；
- 增加引用中的数字及指标 / 数据集 / 模型关键词一致性检查，发现不一致时写入 `parse_warnings` 并标记需复核；
- 新增去重和数字一致性单元测试。当前离线 holdout 基线为 8 条问题：类别准确率 1.00、严重度 Macro-F1 0.905、P1 漏报率 0.25；该指标未因静态 AI 标注回归集重跑而改变，仍需在真实 HY3 配置下复测。

### 阶段 4：人工复核工作流

目标：允许作者修正 AI 判断，并保留审计痕迹。

任务：

- 问题卡片增加“修改等级、修改类别、确认证据、标记误报”；
- 保存 AI 原始值和人工修订值；
- 支持批量将 P3 降级为忽略；
- 支持“需要人工复核”筛选；
- 导出时区分 AI 判断和人工确认。

验收标准：

- 人工修改后刷新页面不会丢失；
- 能查看修改前后的差异；
- 人工确认不能破坏原始证据记录。

阶段 4 实施记录（2026-08-31）：

- 问题卡片展示 AI 原始严重度 / 类别与当前用户修订值；
- 保留严重度、类别、证据判断、处理状态、复核结论和备注编辑能力；
- 增加 `需人工复核` 和 `已忽略` 状态，支持将全部 P3 批量标记为已忽略；
- Markdown 导出明确区分 AI 原始判断和当前采用值，并保留人工结论与备注；
- 保存继续使用现有项目存储和确定性重算流程，刷新页面不会丢失修订；
- 新增 AI 原始值、用户修订值及 `已忽略` 状态的持久化测试。

### 阶段 5：轻量修改稿对比

目标：用低复杂度方式帮助作者判断修改稿是否降低了投稿风险，不强行替代人工判断。

任务：

- 上传修改稿后重新生成评审，并保存独立版本记录；
- 使用稳定 `issue_id`、类别和标题相似度进行一对一的轻量匹配；
- 显示评分 / 五档建议变化，以及已消失、仍存在、新增问题；
- 对低置信或无法匹配的问题标记“待确认”，不强行判定；
- 暂不实现问题拆分、合并和复杂语义追踪。

验收标准：

- 修改稿可以独立保存并重新打开；
- 已消失、仍存在和新增问题能分别统计；
- 低置信匹配会显式提示待确认；
- 版本差异与问题状态可以同时查看。

阶段 5 实施记录（2026-08-31）：

- 保留现有上传、重评、差异摘要、评分变化和问题统计页面；
- 将跨版本匹配收敛为一对一贪心匹配，避免一个新问题被重复计入多个旧问题；
- 明确低置信匹配仅供用户确认，不自动宣称问题已解决；
- 暂不加入问题拆分、合并和复杂语义相似度模型。

### 阶段 6：评审标准版本化

目标：保证不同会议标准下的历史评审可解释。

任务：

- 为每个会议 rubric 增加版本号和更新时间；
- 记录报告生成时使用的 rubric 版本；
- 显示不同 rubric 下评分变化的原因；
- 自定义权重保存为项目级配置；
- 增加 rubric 配置校验，权重总和必须为 1 或自动归一化。

验收标准：

- 历史报告不会因当前 rubric 更新而改变显示；
- 同一论文切换会议标准后能明确说明差异来自哪些维度。

阶段 6 实施记录（2026-08-31）：

- 增加稳定的 rubric catalog 元数据：会议版本、更新时间和标准说明；
- 自定义权重经过统一归一化，并根据权重内容生成稳定版本指纹；
- 报告保存 rubric 版本、更新时间、说明和实际使用的六维权重；
- 修改稿复审沿用原报告的 rubric 权重，避免因当前页面设置变化而改变历史评分口径；
- 修改稿对比页显示评分变化及六维变化，并在 rubric 不同时明确提示不能直接归因于论文修改；
- Markdown 导出包含 rubric 版本、更新时间、说明和权重快照；
- 新增 rubric 版本稳定性和自定义权重指纹测试。

### 阶段 7：性能、后台和失败恢复

目标：让长论文和失败请求不会阻塞或丢失任务。

任务：

- 评审任务继续使用后台队列；
- 增加阶段级进度：解析、检索、生成、证据校验、保存；

阶段 7 实施记录（2026-08-31）：

验收标准：

## 五、评审页布局与信息架构优化

### 5.1 设计结论

这次优化的核心不是继续增加评审角色，而是让单篇 AI 评审更快回答三个问题：

1. 当前最可能被拒的原因是什么？
2. 这些判断是否有论文原文证据？
3. 投稿前应该先改什么？

因此，页面应围绕“模拟结果 → 投稿风险 → 证据 → Action Plan”组织，而不是围绕一长串评审段落组织。

### 5.2 顶部结果区

采纳以下方案：

- 删除容易被误认为可点击决策的五档大按钮视觉；
- 保留五档等级作为只读结果和轻量标尺；
- 顶部只突出：

```text
模拟评审结果   Weak Reject   4.0 / 10   置信度 4 / 5
```

- 删除整条超长蓝色“评审摘要”；
- 改为 60–100 字的“当前主要拒稿风险”；
- 完整评审文字放入可展开区域。

由于产品已经移除多人评审，因此禁止显示 Reviewer 1/2/3 分布和 Meta Reviewer。统一使用：

```text
当前主要拒稿风险：创新性证据不足、关键消融实验不足、学习效果验证有限
```

“Meta Review”统一改名为“综合结论”或“AI 评审总结”。

### 5.3 右侧首屏信息顺序

右侧首屏从“主要优点”调整为“投稿风险”：

```text
投稿风险

P1 · 创新性证据不足                         High
Director Agent 与已有方法的差异还不够明确。
证据 3 处 · 定位原文 →

P1 · 关键消融实验不足                       High
无法判断 hierarchical explanation、RAG、LoRA 各自贡献。
证据 2 处 · 定位原文 →

P2 · 学习效果验证有限                       Medium
当前主要依赖专家评价，缺乏真实学习效果验证。
```

主要优点保留，但折叠为“论文已有优势（5 项）”，避免风险信息被大量浅蓝卡片淹没。

### 5.4 评审卡片内容

每条风险卡片固定显示：

- 严重度：P0/P1/P2/P3；
- 问题标题；
- 一句话影响；
- 证据数量和“定位原文”入口；
- 关联的修改任务；
- 当前状态。

优势卡片使用有信息量的标题，例如：

- 系统流程完整；
- 内容组织较清晰；
- 考虑生成错误控制。

视觉规则：

- 普通内容使用白底和灰色分隔线；
- 红色/橙色只表示 P0/P1 风险；
- 绿色表示优势；
- 蓝色只用于链接、证据定位和交互控件；
- 避免连续使用相同浅蓝背景。

### 5.5 综合结论

“最终建议”不再使用整段黄色警告框，改为结构化的“综合结论”：

```text
综合结论                         Weak Reject

总体判断
论文具有明确应用场景和完整系统实现，但当前实验和创新性证据不足以支撑接收。

主要拒稿原因
创新性 → 消融实验 → 学习效果

[展开完整 AI 评审总结]
```

默认只展示摘要和拒稿原因，完整长文本由用户主动展开。

### 5.6 投稿前 Action Plan

将“最优先修改的事项”升级为可操作任务：

```text
投稿前 Action Plan

P0 · 实验
增加核心模块消融实验
分别验证 hierarchical explanation、RAG、LoRA 对最终效果的贡献。
关联问题：创新性证据不足、消融实验不足

P0 · Contribution
重新明确核心创新点
对比已有 multi-agent instructional video generation 方法。

P1 · Evaluation
补充真实学习效果实验
```

后续可增加“标记已完成”，但不恢复作者答辩模块；完成状态表示作者的内部修改进度，不表示 AI 已确认论文通过评审。

### 5.7 PDF 与问题联动

现有“查看依据”功能继续深化为双向联动：

- 点击“定位原文”后，左侧自动跳转页码并高亮句子/段落；
- 右侧当前问题保持选中；
- PDF 工具栏显示“当前问题 · 证据来自第 X 页”；
- 点击 PDF 高亮时，右侧展示对应问题和评审判断；
- 没有可定位证据的问题明确显示“需人工复核”。

这是优先级高于换配色、动画和圆角样式的交互，因为它直接建立“评审判断 → 论文证据”的可信链路。

### 5.8 尺寸与滚动

- 左右比例目标：论文区约 60%–62%，评审区约 38%–40%；
- 左右区域独立滚动；
- 右栏固定在约 460–520px 范围；
- 顶部论文信息栏和右侧 Tab 在滚动时保持可见；
- PDF 工具栏压缩为：

```text
‹  1 / 9  ›  │  −  100%  +  │  适应宽度
```

### 5.9 UI 改造执行顺序

1. 顶部结果区和核心判断；
2. 右侧首屏改为投稿风险；
3. 优势卡片标题和视觉简化；
4. Action Plan 和完成状态；
5. PDF 与问题双向联动；
6. 左右宽度、独立滚动、sticky 工具栏；
